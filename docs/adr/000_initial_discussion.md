# Architecture Specification: daisy-gutenberg

## 1. Executive Summary & Architectural Vision

This document details the architectural strategy for **`daisy-gutenberg`**, a WordPress Gutenberg block collection powered by **DaisyUI** and **Tailwind CSS**.

The primary goal of `daisy-gutenberg` is to produce lightweight, semantic, and highly maintainable Gutenberg blocks using Block API v3, TypeScript, and modern WordPress tooling (`@wordpress/scripts`). By pairing DaisyUI with Gutenberg, we leverage semantic CSS component classes (e.g., `btn`, `card`, `badge`) rather than scattering verbose, low-level Tailwind utility strings across serialized post content.

---

## 2. Key Technical Challenges & Mitigation Strategies

### 2.1 Tailwind Preflight & Gutenberg Admin Collisions
* **The Challenge:** Tailwind CSS includes "Preflight", an aggressive CSS reset based on `modern-normalize`. Loading Preflight inside the WordPress Block Editor (`wp-admin`) resets core editor styles, breaks Gutenberg sidebars, distorts SVG icons, and overrides native core controls.
* **The Mitigation Strategy:**
  * Disable standard Tailwind Preflight in the build configuration, **or**
  * Scope preflight strictly to the editor canvas (e.g., `.editor-styles-wrapper` or the editor iframe body) via PostCSS nesting.
  * Provide a selective, isolated reset that targets only `daisy-gutenberg` selectors without polluting the admin shell.

### 2.2 Design Tokens & Theme Synchronization
* **The Challenge:** DaisyUI relies on HTML `data-theme` attributes and internal semantic CSS variables (`primary`, `secondary`, `accent`, etc.). WordPress Full Site Editing (FSE) manages styles via `theme.json` and produces variables with the `--wp--preset--color--*` naming convention.
* **The Mitigation Strategy:**
  * Establish DaisyUI as the design token source of truth.
  * Provide theme selector controls on wrapper blocks (such as a Section or Hero block) to apply `data-theme="<theme_name>"` at runtime.
  * Optionally, map Gutenberg's `theme.json` color definitions to DaisyUI CSS variables using a custom CSS bridge.

### 2.3 Static Blocks vs. Dynamic Blocks
* **Decision Rule:**
  * **Static Blocks (`save.tsx`):** Used for structural and presentation components (Buttons, Badges, Cards, Dividers, Alerts). These compile directly to clean, standard HTML attributes and DaisyUI classes. This guarantees zero server-side rendering overhead and maximum caching efficiency.
  * **Dynamic Blocks (`render.php`):** Reserved exclusively for components that fetch dynamic server data (e.g., query loops styled as DaisyUI cards) or interactive components leveraging the WordPress Interactivity API (e.g., complex dynamic modals, drawers, or live filters).

## 4. Core Subsystems

### 4.1 Attribute-to-Class Mapping Layer
To ensure long-term stability and prevent block validation deprecation errors, block attributes must not store raw Tailwind strings. Instead:
* Blocks store structured, semantic attributes (e.g., `variant: "primary"`, `size: "sm"`, `isOutline: true`).
* A deterministic class mapping function generates the appropriate DaisyUI class string (e.g., `btn btn-primary btn-sm btn-outline`) dynamically within `edit.tsx` and `save.tsx`.
* If a DaisyUI class changes in a future library release, changing the mapping function updates the entire site without breaking serialized post validation.

### 4.2 Shared Inspector Controls (Sidebar UI)
DaisyUI uses consistent design modifiers across components. A shared library of custom Inspector Controls (wrapping `@wordpress/components`) will be created for:
* **Semantic Colors:** Primary, Secondary, Accent, Neutral, Info, Success, Warning, Error.
* **Component Sizing:** Extra Small (`xs`), Small (`sm`), Medium (`md`), Large (`lg`).
* **Visual Modifiers:** Outline, Ghost, Glass, Wide, Block.

### 4.3 Compound Components via `InnerBlocks`
For multi-part components (such as Cards, Modals, and Accordions), blocks are split into parent-child architectures using WordPress `InnerBlocks`:
* **Card (`daisy-gutenberg/card`):** Defines overall layout, borders, shadow, and background.
  * **Card Body (`daisy-gutenberg/card-body`):** Handles internal content padding and spacing.
    * **Card Title (`daisy-gutenberg/card-title`):** RichText or core Heading wrapper.
    * **Card Actions (`daisy-gutenberg/card-actions`):** Container restricted to accepting `daisy-gutenberg/button` blocks.

This ensures design system integrity while offering editors flexible content assembly.

## 5. Build Toolchain Strategy

* **Foundation:** `@wordpress/scripts` provides the default build setup, dependency extraction (`*.asset.php`), and automated block discovery.
* **Webpack Extension:** A custom `webpack.config.js` will extend the default `@wordpress/scripts` configuration to include `postcss-loader` for Tailwind CSS and DaisyUI processing.
* **Multi-Block Compilation:** Multi-block discovery automatically registers each folder inside `src/blocks/` that contains a `block.json`.
* **Asset Loading Strategy:**
  * Compiled styles will be bundled into a shared stylesheet to prevent duplicate Tailwind/DaisyUI utility outputs across individual blocks.
  * Shared assets are enqueued centrally via the plugin PHP entry point (`daisy-gutenberg.php`).
